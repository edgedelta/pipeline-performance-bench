# Benchmark report: AI involvement and development prompts

Our goal is impartial, objective analysis across the tested agents. We use AI-assisted development to support consistent implementation and reporting, and publish these instructions so readers can assess potential bias, scrutinize the methodology, and propose corrections. Openness about the prompts is part of that goal: AI assistance is a tool, not a guarantee of neutrality. Conclusions must remain supported by reproducible measurements and explicit comparison rules.

The benchmark harness and report generator were developed iteratively with an AI coding assistant at the repository owner's direction. The daily workflow runs code, collects measurements, validates them, and renders Markdown using Python. It does **not** send results to an AI model or invoke a report-writing prompt at runtime.

This document was added on September 17, 2026. It preserves relevant verbatim excerpts from the owner's development requests and summarizes subsequent requirements. It is not a complete conversation transcript or a claim that a single prompt generated each release. The release's source commit, workflow, raw measurements, and checksums are the evidence for what actually ran. AI involvement does not establish neutrality or independently validate the benchmark.

## Original development request — verbatim excerpts

> Update this repository’s daily benchmark job and release-note generation to include fixed-throughput resource comparisons and detailed AWS machine specifications. Implement and validate the changes; do not just propose a plan.
>
> Inspect the current workflow, load generator, resource monitoring, summarizer, report templates, and release publication logic first.
>
> Preserve the existing throughput benchmarks and reports.

> Define and document a measurable “sustains target” criterion with an explicit tolerance. Do not claim backlog stability unless measured.
>
> Distinguish agent capacity limits from load-generator limitations and invalid runs.
>
> Never extrapolate fixed-rate results from existing best-throughput results.

> Use matching supported scenarios for cross-agent aggregate comparisons.
>
> Do not present lower resource usage as an equal-throughput win when an agent fails to sustain the target.

> Retain raw measurements and structured data in release assets so every reported value can be reproduced. Extend data.json and report.md consistently, and ensure the actual GitHub release body generated by the daily job includes the new sections.

> Preserve unsupported, missing, invalid, and capacity-limited outcomes as distinct statuses.
>
> Preserve existing retry, error, and ambiguous-delivery accounting.
>
> Continue labeling throughput as acknowledged HTTP ingestion unless durable delivery is independently verified.
>
> Handle older result files without fabricating new metrics.

## Subsequent requirements — summarized, not verbatim

- Use current agent installation channels and record the installed versions. Run agents in parallel on separate identically configured AWS instances, with sequential scenarios and rate tiers.
- Replace the daily Go load generator with the Rust worker implementation. Reuse measured fixed-rate windows for the bounded throughput search, retaining generator calibration and explicit shortfall statuses.
- Include the 125,000 logs/sec fixed-rate tier. Stop higher tiers after a shortfall, label them as untested, and never infer their performance.
- Report actual acknowledged logs divided by measured duration, rather than substituting configured targets. Show CPU, average and peak memory, and efficiency from the same selected measurement window.
- Keep the release title format `Benchmark Report - YYYYMMDD-HHMMSS`. Keep tables expanded, consolidate shared hardware settings, and keep detailed diagnostics in downloadable assets.
- Sort fixed-rate targets highest first. Highlight the highest valid measured throughput, including ties; highlight CPU efficiency leaders only among passing agents at the same scenario and target. Apply the rules to every agent.
- Explain generator uncertainty and tested ceilings. A bounded search does not establish maximum agent capacity. HTTP acknowledgements do not prove durable delivery or stable agent backlog.
- Add a top-of-report disclosure of AI involvement with a link to these development instructions.
- Lead that notice with the purpose: support impartial, objective analysis and make the instructions open to scrutiny, rather than merely disclose AI usage.

The request to display high fixed-rate tiers first included the observation that Edge Delta Rust performed best there. That is a presentation choice made by the repository owner, not evidence of independent or neutral study design. The measurements, exclusions, sort rules, and highlighting rules remain inspectable in the source and assets.

## How to reproduce a report

Use the source revision recorded in the release and its downloaded raw measurement assets. [tools/summarize.py](../tools/summarize.py) computes structured results, [tools/release_report.py](../tools/release_report.py) renders the reader-facing tables, and [tools/publish_release.py](../tools/publish_release.py) validates and publishes the release. [tools/capacity.py](../tools/capacity.py) and [tools/fixed.py](../tools/fixed.py) define throughput selection and target attainment; the [methodology](fixed-throughput.md) documents units and measurement policy.

These links resolve to the same document revision when opened from a commit-pinned release link. Inspect the run's provenance and code for exact settings; requirements above describe development intent and do not replace measured evidence.
